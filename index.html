01 About

From raw data to a service people actually use.

I'm Yash Kolekar — a Data Scientist / AI Engineer with 2+ years building Generative AI systems end to end: retrieval over private knowledge, agents that call real tools, and the Python services that put both in front of users.

Most of my work is the unglamorous half of GenAI — deciding how a document gets chunked, why a retrieval returns the wrong passage, what a prompt should refuse to answer. I build on LangChain, LangGraph and CrewAI, with Pinecone, ChromaDB and FAISS behind them, and I tune accuracy through retrieval and prompt design before reaching for a fine-tune.

Alongside that sits classical ML — classification, clustering and forecasting with Scikit-learn, PyTorch and XGBoost — plus the SQL and ETL that keeps the inputs honest. Everything ships the same way: FastAPI services, Docker containers, CI/CD on Jenkins, PyTest for the parts that must not break, and AWS underneath.

Right now I'm at Infosys in Bengaluru working on an enterprise AIOps assistant. I'm an immediate joiner and happy to work remote.

03

Agent · tool calling

Student Enrollment Assistant Agent

A conversational agent for university admissions that answers on programs, deadlines and application status through real tool calls rather than model memory. Three custom tools — get_program_info, check_application_status and get_deadlines — with structured inputs and outputs; the agent reasons about which to call.

Multi-turn session memory carries the applicant ID across the conversation, and anything out of scope escalates to a human counsellor instead of being guessed at.

Demo project — the three tools are backed by mock data, not a live admissions database.

04

Agent · LangGraph · code on GitHub

Travel Reimbursement Approval Agent

Reviews an employee travel claim against policy, receipts, limits and approval rules, then returns a structured decision — Approve, Partially Approve, Reject or Manual Review — as a LangGraph state machine: intake → retrieve → run_tools → reason → validate.

The design choice that matters: deterministic tools own the numbers, so the arithmetic stays correct and auditable, while the LLM owns judgement and explanation. Six tools cover policy lookup (RAG over chunked policy), receipt completeness, per-item limits, duplicate detection, approval bands and output validation. Anything missing, duplicated, over the band or low-confidence routes to a human instead of being guessed at.

It also runs with zero API keys — with no LLM configured, a transparent rule engine returns the same schema, so the demo never fails shut.

Case-study prototype — policy and claim data are mock.

05 How I work

The habits behind the stack.

01

Prototype through production

A notebook that works is the start, not the deliverable. I take the same piece of work through API design, tests, containers and deployment.

02

Retrieval before fine-tuning

Most "the model is wrong" problems are retrieval problems. I fix chunking, embeddings and context first, and fine-tune when that genuinely runs out.

03

Honest scope

I say what a system can't do. Agents escalate instead of inventing answers, and I mark a skill "basic" rather than padding a list.

04

Written down

Code reviews, documentation and tests are part of the work. Someone else has to run this after I hand it over.
